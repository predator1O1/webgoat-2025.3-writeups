# SQL Injection (mitigation)

## Overview

The **SQL Injection (mitigation)** lesson demonstrates how SQL injection vulnerabilities can be prevented and why input validation alone is not a sufficient defense. The exercises cover parameterized queries, `PreparedStatement`, safe JDBC code, weaknesses in keyword-based filtering, and a Boolean-based SQL injection through an `ORDER BY` clause.

The lesson also demonstrates an important defensive principle: **user-controlled input should not be concatenated into SQL statements**. Parameterized queries should be used wherever values are supplied by the user, while input validation should be treated as an additional control rather than the primary SQL injection defense.

## Task 4 — Using `PreparedStatement`

**Task:** Complete the incomplete code so that the application retrieves a user's status based on the user's name and email address without being vulnerable to SQL injection.

The lesson provides a JDBC connection and asks for a safe query using a `PreparedStatement`. The query contains two string parameters, represented by `?` placeholders.

I completed the missing JDBC code by preparing the SQL statement and binding the user-supplied values through `setString()` rather than concatenating them into the SQL query.

The resulting structure is:

```java
PreparedStatement statement = conn.prepareStatement(
    "SELECT status FROM users WHERE name=? AND mail=?"
);

statement.setString(1, name);
statement.setString(2, mail);
```

I submitted the completed code, and WebGoat confirmed that the assignment was successfully completed.

![PreparedStatement solution completed](../assets/a3-injection/sql-injection(mitigation)/01-task-4-prepared-statement.png)

### Why this prevents SQL injection

The `?` placeholders separate SQL syntax from user-controlled data. The supplied values are bound as parameters rather than being interpreted as part of the SQL statement.

## Task 5 — Writing Safe JDBC Code

**Task:** Write Java/JDBC code from scratch that connects to the database, executes a SQL query that is immune to SQL injection, and contains at least one string parameter.

The lesson provides the database connection constants `DBURL`, `DBUSER`, and `DBPW`. I used a `PreparedStatement` with two parameters and supplied the values using `setString()`.

The query I used was structured as follows:

```java
try (Connection conn = DriverManager.getConnection(DBURL, DBUSER, DBPW)) {
    PreparedStatement statement =
        conn.prepareStatement("SELECT * FROM users WHERE name=? AND mail=?");

    statement.setString(1, "John");
    statement.setString(2, "john@example.com");

    ResultSet result = statement.executeQuery();
} catch (SQLException sqle) {
}
```

I submitted the code, and WebGoat confirmed that the code can prevent an SQL injection attack.

The lesson explains that input validation by itself is not a reliable defense against SQL injection. The application attempts to restrict SQL injection by filtering specific input, but the filtering can be bypassed.

### Bypassing keyword filtering

The important weakness is that the application attempts to identify dangerous SQL keywords rather than preventing SQL syntax from being interpreted as part of the query.

I used SQL comment syntax to alter the appearance of the input to the filter while still producing valid SQL after the application's filtering step. This demonstrates why blacklisting individual keywords is not a reliable SQL injection defense.

The successful request returned database records and WebGoat marked the assignment as completed.

![Successful SQL injection using keyword-filter bypass](../assets/a3-injection/sql-injection(mitigation)/06-task-8-successful-union.png)

### Lesson takeaway

Filtering keywords such as `SELECT`, `FROM`, or `UNION` does not address the underlying problem. An attacker can often represent SQL syntax in another form, use comments, encoding, alternate syntax, or exploit keywords that were not included in the filter.

The correct mitigation is to use **parameterized queries / prepared statements** instead of attempting to sanitize SQL syntax manually.

## Task 12 — SQL Injection Through the `ORDER BY` Field

**Task:** Perform SQL injection through the `ORDER BY` field to determine the IP address of the `webgoat-prd` server. The final part of the IP address is hidden to make the exercise practical.

The application displays a list of servers and allows the client to influence the value used in the `ORDER BY` clause. The submission field itself is not vulnerable; the injection point is the column/order expression used to retrieve and sort the server list.

![ORDER BY SQL injection assignment](../assets/a3-injection/sql-injection(mitigation)/10-task-12-order-by-injection.png)

### Building the Boolean condition

I used a `CASE WHEN EXISTS(...)` expression as the `ORDER BY` payload. The `EXISTS` condition checks whether a server matching the specified hostname has an IP address beginning with a guessed character.

The payload follows this structure:

```sql
CASE WHEN EXISTS(
    SELECT id
    FROM servers
    WHERE hostname = 'webgoat-prd'
      AND substring(ip,1,1) = '1'
    THEN id
    ELSE ip
END
```

I changed the `substring()` position and guessed character while observing the ordering of the returned server list.

![First character test](../assets/a3-injection/sql-injection(mitigation)/11-task-12-ip-position-test-1.png)

![Next character test](../assets/a3-injection/sql-injection(mitigation)/12-task-12-ip-position-test-2.png)

![Additional character test](../assets/a3-injection/sql-injection(mitigation)/13-task-12-ip-position-test-3.png)

![Additional character test](../assets/a3-injection/sql-injection(mitigation)/14-task-12-ip-position-test-4.png)

![Final character test](../assets/a3-injection/sql-injection(mitigation)/15-task-12-ip-position-test-5.png)

### How the Boolean oracle works

The actual query running inside the application is:

```sql
SELECT id, hostname, ip, mac, status, description
FROM SERVERS
WHERE status <> 'out of order'
ORDER BY <your payload>
```

The payload is inserted after `ORDER BY`:

```sql
ORDER BY CASE WHEN EXISTS(
    SELECT id
    FROM servers
    WHERE hostname = 'webgoat-prd'
      AND substring(ip,1,1) = '1'
    THEN id
    ELSE ip
END
```

The `EXISTS` statement asks:

> **Is there at least one server whose hostname is `webgoat-prd` AND whose IP's first character is `1`?**

The attack is essentially:

```text
Guess a character
      ↓
substring(ip, position, 1) = guess
      ↓
   ┌───────────────┐
   │               │
 TRUE            FALSE
   ↓               ↓
ORDER BY id     ORDER BY ip
   ↓               ↓
sequential       different
   list            order
```

This means the application has accidentally created a **Boolean oracle**. The application does not directly reveal whether the guessed character is correct. Instead, the truth value changes the expression used for sorting, and the resulting order of the server list becomes the observable side channel.

I used this behavior to determine the hidden characters of the IP address one position at a time.

### Result

After determining the required characters, I entered the resulting IP address into the submission field:

```text
104.130.219.202
```

WebGoat confirmed that the assignment was successfully completed.

## Key Takeaways

- `PreparedStatement` is the primary defense against SQL injection when user-controlled values are used in SQL statements.
- Parameterized queries separate SQL syntax from data supplied by the user.
- Input validation is useful as a secondary control but should not be treated as the primary SQL injection defense.
- Keyword blacklists can often be bypassed through SQL comments, encoding, alternate syntax, or other representations of SQL tokens.
- SQL injection is not limited to `WHERE` clauses. Any SQL context that accepts attacker-controlled syntax, including `ORDER BY`, can potentially become an injection point.
- The `ORDER BY` exercise demonstrates how a vulnerable application can unintentionally expose a **Boolean oracle** through observable differences in response ordering.


## Remediations

The exercises in this lesson demonstrate several weaknesses that should be addressed at the application and database layers.

### 1. Use parameterized queries

The primary remediation for SQL injection is to use parameterized queries / prepared statements for values supplied by users. In Java, `PreparedStatement` should be used instead of concatenating user-controlled data into SQL strings.

For example:

```java
String query = "SELECT status FROM users WHERE name=? AND mail=?";
PreparedStatement statement = conn.prepareStatement(query);

statement.setString(1, name);
statement.setString(2, mail);
```

This keeps SQL syntax separate from user-controlled values and prevents input from changing the intended structure of the query.

### 2. Do not rely on keyword blacklists

Filtering strings such as `SELECT`, `UNION`, or `FROM` is not a reliable SQL injection defense. Attackers may use comments, encoding, alternate syntax, or other representations that bypass a denylist.

The application should remove the need to interpret user input as SQL syntax rather than attempting to identify every possible malicious representation.

### 3. Treat input validation as a secondary control

Input validation should still be performed to enforce the expected type, format, length, and range of each input. However, validation should complement parameterization rather than replace it.

Allowlist validation is preferable to trying to enumerate malicious input with a denylist.

### 4. Handle dynamic SQL identifiers safely

Parameter placeholders cannot be used for every part of a SQL statement. For example, dynamically selecting a column name or sort direction may require a different design.

For the `ORDER BY` case demonstrated in Task 12, the application should map a user-controlled value to a small, predefined set of safe column names or sort directions rather than inserting the raw value into the query.

For example:

```java
String orderBy;

switch (requestedSort) {
    case "hostname":
        orderBy = "hostname";
        break;
    case "ip":
        orderBy = "ip";
        break;
    default:
        throw new IllegalArgumentException("Invalid sort field");
}

String query =
    "SELECT id, hostname, ip, mac, status, description " +
    "FROM servers " +
    "WHERE status <> 'out of order' " +
    "ORDER BY " + orderBy;
```

Here, the value appended to the query is selected exclusively from application-controlled constants rather than copied directly from the request.

### 5. Apply least privilege to the database account

The application's database account should have only the privileges required for the application's normal functionality. Restricting database permissions does not fix SQL injection, but it can reduce the impact if an injection vulnerability is exploited.

For example, an account used only for reading application data should not unnecessarily have permissions to modify or drop database objects.

### 6. Review and test every SQL execution path

Security reviews should identify database queries that use string concatenation, dynamic SQL construction, or user-controlled SQL fragments. Automated testing and code review should verify that user-controlled values reach parameterized APIs rather than raw SQL execution.
